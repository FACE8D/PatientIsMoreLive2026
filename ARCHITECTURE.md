# Архитектура Clinic Companion

## 1. Назначение и границы

Приложение помогает собирать самоотчёты, хранить историю, визуализировать динамику и подготовить врачу информацию для обсуждения. Оно не является автономным диагностическим механизмом. Все клинически значимые решения — диагноз, маршрутизация, начало/изменение/отмена терапии — принимаются специалистом после проверки данных.

## 2. MVP-топология

```text
Browser (vanilla JS/CSS)
       │ same-origin HTTP + JSON + session cookie + CSRF token
       ▼
Python ThreadingHTTPServer
  ├── auth/session + RBAC + patient/doctor relationship checks
  ├── domain/API handlers
  ├── questionnaire loader (data/questionnaires/*.json)
  ├── server-side scoring + safety rules
  ├── deterministic summary/AI placeholder
  └── audit log
       │ parameterized SQL / foreign keys
       ▼
SQLite (local file)
```

В текущем MVP нет отдельного фронтенд-сборщика и внешних библиотек. HTTP доступен на loopback. Для многопользовательского развёртывания этот однопроцессный локальный вариант нужно заменить полноценной серверной инфраструктурой.

## 3. Роли и контроль доступа

- **Врач:** видит связанные с его учётной записью карточки, результаты шкал, дневники, визиты, назначения, рекомендации и сигналы; может создать/архивировать карточку, сделать клиническую запись, создать черновик схемы и вручную подтвердить/приостановить/остановить её.
- **Пациент:** видит только свою карточку, свои самоотчёты и опубликованные рекомендации, утверждённые врачом схемы, свой календарь и переписку. Черновики лечения и черновики рекомендаций не выдаются в пациентском API. Клинические шкалы, включая C-SSRS, закрыты от прохождения пациентом через этот поток.
- Сервер независимо проверяет роль и связь пациент-врач на каждом защищённом endpoint. Скрытие кнопки в браузере не считается защитой.

## 4. Главные таблицы

- `users`, `sessions`: учётная запись, хэш пароля, серверный хэш токена сессии, CSRF и срок действия.
- `patients`: связанный пользователь пациента, ведущий врач, демографические поля, согласуемая необязательная функция цикла, архивный статус.
- `entries`: датированные записи дневников с JSON payload.
- `questionnaire_results`: версия инструмента, ответы и рассчитанный сервером результат.
- `appointments`, `visits`: календарные события (врач создаёт приёмы/напоминания, пациент — только личные события) и заметки приёмов/план наблюдения.
- `medication_plans`, `medication_logs`: плановая схема и отметка пациента о фактическом приёме/пропуске/нежелательной реакции.
- `recommendations`, `messages`, `alerts`, `audit_log`: рекомендации с жизненным циклом черновик→публикация, чат, сигналы безопасности и история значимых действий.

Доступ к БД использует параметризованные запросы и внешние ключи SQLite. Пароли хэшируются PBKDF2-HMAC-SHA256; в БД сохраняется хэш случайного session-token, а не сам токен. Прототип всё ещё не заменяет полноценное управление идентификацией, MFA, rate limiting и независимый security review.

## 5. Поток данных пациента

1. Пациент сохраняет дневник, отметку приёма или результат самоопросника.
2. Сервер валидирует размер и форму входных данных, сохраняет их к карточке пациента и при определённых правилами признаках открывает алерт.
3. При следующем запросе карточки данные доступны ведущему врачу в общей истории; не требуется ручное пересылание.
4. Врач оценивает данные, фиксирует визит, обрабатывает alert, готовит рекомендацию или черновик схемы.
5. Пациент получает опубликованную рекомендацию/подтверждённую схему. Черновик не отображается.
6. История остаётся при архивировании карточки; вход архивированного пациента выключается.

## 6. Опросники как подключаемые определения

Один JSON-файл — один instrument/version. Файл хранит формулировки, тип ответа, варианты, числовые значения, группы, источники, лицензионный статус и правила подсчёта. Интерфейс строит доступные формы из вопроса, сервер самостоятельно вычисляет баллы. Для клинических шкал используется `respondent: clinician`, и API сверяет роль.

Прежде чем менять/подключать версию, надо:

1. подтвердить источник и права на воспроизведение/перевод;
2. определить период оценки, обязательность, ветвления и правила пропуска;
3. проверить каждую опцию, обратные вопросы, подшкалы и интервалы результата;
4. добавить граничные unit-тесты и интеграционные тесты на сигналы;
5. не менять исторические определения незаметно — version ID должен соответствовать определению, использованному при заполнении.

### Оговорки, уже зафиксированные в файлах

- HCL-32 (из отдельного PDF) и HCL-33 (из ODT) не объединяются и не получают общий порог.
- C-SSRS — отдельный врачебный сценарий; исходный документ говорит о применении обученным лицом. Встроенные алерты — триггеры проверки, не валидированный суммарный прогноз риска.
- BDI-21: приложение требует один ответ на категорию для однозначного счёта; источник разрешает отметить несколько утверждений при равной применимости. Это расхождение должно быть разрешено по авторизованной версии перед клиническим использованием. Дополнительный вопрос о намеренном похудении — контекстный и не суммируется.
- HDRS-17: приложенный ключ не определяет категорию ровно для 23 баллов; система отображает этот промежуток без выдуманной категории.
- GAD-7, BAI, SCL-90-R и ИТТ содержат примечания о точных ограничениях интерпретации/порогах в исходном комплекте.
- В некоторых инструментах есть тексты/версии с потенциальными ограничениями авторского права. Флаг `license_review_required` не означает, что право получено; он означает, что требуется проверка.

## 7. Правила безопасности и алертинг

MVP умеет открыть внутрисистемный alert на некоторых ответах, дневниковых флагах и сообщениях о нежелательных реакциях. Алерт хранит источник, уровень, статус и действия подтверждения. Приоритеты/условия являются прозрачными техническими правилами прототипа, а не медицински валидированным классификатором.

**Не реализовано:** круглосуточная фоновая проверка, гарантированная доставка внешнего уведомления, push/SMS, эскалация при отсутствии подтверждения, дежурная смена, SLA и fail-safe для недоступного сервера. Нельзя обещать пациенту, что врач увидит критический ответ в реальном времени. В UI это явно отмечено.

## 8. Лекарства и схемы

`data/medications.json` отделён от кода и содержит 17 версионированных профилей с фармакокинетикой, противопоказаниями, предосторожностями, взаимодействиями, нежелательными реакциями и мониторингом. `data/treatment_schemes/*.json` содержит 11 версионированных схем с `clinical_detail_sections`, шагами, правилами безопасности и ссылками на конкретные разделы/страницы переданных документов. Врач может читать эти сведения во встроенном окне, не открывая PDF, и создавать на их основе план конкретного пациента. Настройки сохраняются в экземпляре плана, не в библиотеке; у активного экземпляра изменения требуют повторного клинического обзора и подтверждения.

Библиотека содержит 17 профилей лекарств (Авиандр® и 16 оставшихся МНН из таблицы стандарта). Моклобемид и милнаципран не включены в доступный каталог. Для каждого заполнены доступные сведения о фармакокинетике, справочном режиме применения, противопоказаниях, предосторожностях, взаимодействиях, нежелательных реакциях и мониторинге, с указанием названий источников. Для «Авиандр®» дополнительно дана прямая ссылка на страницу конкретного препарата; для других веществ основная ссылка «Видаль» ведёт на монографию действующего вещества. Это клинические справочные сводки, а не полные официальные инструкции. В таблице стандарта первичной медико-санитарной помощи при депрессиях (ремиссии) в исходной таблице приведены средние суточные и курсовые дозы для 18 МНН; два вещества исключены из доступного каталога, поэтому сведения о дозах по ним не предлагаются; оставшиеся средние значения не должны автоматически интерпретироваться как индивидуальные назначения. Адресный поиск ГРЛС фильтрует результаты по МНН, но не подтверждает единственную актуальную запись. Врач сверяет торговое наименование, производителя, форму, дозировку и редакцию инструкции по официальному реестру.

Отдельная проверка целостности источника отмечает флуоксетин: в таблице стандарта первичной медико-санитарной помощи при депрессиях (ремиссии), печатная страница 6, единица указана как «мл». Значение сохранено буквально, помечено как требующее проверки и не должно переноситься в назначение до сверки с исходной/действующей редакцией и инструкцией. Копия стандарта имеет незаполненные реквизиты приказа и не подтверждает текущую юридическую актуальность.

Черновик схемы требует явного подтверждения врачом и отметки в UI о том, что актуальная инструкция проверена. После подтверждения схема становится пациенту видимой и может выводить расписание, заданное врачом, на календарь. В MVP нет автоматической проверки взаимодействий, аллергий, лабораторных показателей или всех индивидуальных ограничений; отсутствие данных не означает отсутствие противопоказаний.

## 9. Архитектура будущего локального ИИ

Рекомендуется отдельный адаптер `ClinicalInferenceService`, вызывающий локальный inference endpoint за границей сервера UI/CRUD. Модель не должна иметь прямой доступ на запись в таблицы назначения и не должна владеть секретами или произвольно исполнять инструменты.

**Вход:** минимизированный профиль пациента, жалобы/функционирование, последовательности баллов с датами, активные/остановленные планы, дневники/приверженность, сигналы безопасности и контекст вопроса врача. Перед передачей — явный список полей, минимизация идентификаторов и аудит использования.

**Выход:** JSON по фиксированной схеме, например:

```json
{
  "summary": [{"text": "...", "evidence_ids": ["result:123"]}],
  "uncertainties": ["..."],
  "safety_concerns": [{"rule_id": "...", "reason": "...", "requires_human_review": true}],
  "questions_for_clinician": ["..."],
  "options_for_discussion": [{"description": "...", "source_ids": ["guideline:..."], "requires_confirmation": true}],
  "not_a_diagnosis": true
}
```

Все поля schema-validate; ссылки на лекарственные/клинические источники должны браться из проверенной версии базы, а не генерироваться текстом модели. UI явно помечает гипотезы/неопределённости. Любое клиническое предложение сохраняется только как draft, врач подтверждает его отдельно. Система должна уметь работать без модели и не считать отсутствие ответа модели отсутствием риска.

**Валидация до запуска:** зафиксировать версию модели и корпус, оценить качество на размеченных специалистами случаях, измерить пропуски критических состояний и ложные тревоги, провести red-team/prompt-injection тесты, журналировать версию и вход/выход с ограниченным доступом, проверять drift, обеспечить локальность хранения и процедуру rollback. Текущая реализация не подключает модель.

## 10. Производственный план

1. Клинический совет и владельцы процессов: определить протоколы safety-alert и маршрутизации; проверить инструменты/лицензии и все материалы ГРЛС.
2. Подтвердить модель угроз, правовые основания/согласия, сроки хранения и границы доступа.
3. Вынести БД и API в защищённую серверную среду, включить TLS, MFA, управление ключами, rate limiting, структурированные защищённые логи, резервное копирование и тест восстановления.
4. Добавить фоновые задачи и надёжную очередь уведомлений с повторной доставкой, ACK/escalation и мониторингом доступности.
5. Расширить медикаментозную базу на основе проверенных структурированных официальных источников; запретить вывод рекомендаций при просроченном источнике.
6. Подключать локальную модель только за строгим schema/API-контрактом и обязательное участие врача.
7. Выполнить независимое security, UX/accessibility и клиническое тестирование на синтетических и разрешённых наборах данных.

## 11. Клиническая карта и принцип «один ввод — много выходов»

Клинический осмотр хранится как одна версионируемая запись `clinical_assessments`: психический статус, риски, функционирование, соблюдение плана, побочные явления, клиническое резюме и план. До подписания это черновик и доступен только врачу. После подписания та же запись становится доступной пациенту в разрешённом объёме, появляется в истории, используется для клинического JSON-отчёта, экспорта FHIR и DICOM SR. Не надо отдельно перенабирать вывод в четыре системы: у каждого обменного представления есть ссылка на исходную запись и время её версии.

Интерфейс использует кликабельную «карту состояния» по областям (настроение/аффект, содержание мыслей, восприятие, активность/сон, функционирование, риск, приверженность и нежелательные явления). Карта вдохновлена принципом модальной рабочей поверхности стоматолога, но не копирует анатомическую карту зубов: клиническая структура соответствует задаче мониторинга психического состояния. Маркеры риска — это статусы для проверки, а не самостоятельные диагностические признаки.

## 12. Схемы лечения — отдельные загружаемые файлы

`data/treatment_schemes/*.json` содержит 11 подключаемых сценариев: тревожная оценка и маршрутизация; сопровождаемая самопомощь при депрессивных симптомах; КПТ/структурированная терапия; поведенческая активация; посильная физическая активность; релаксация; согласование начала/мониторинга антидепрессанта; обсуждение профилактики рецидива; постепенное снижение/отмена; регистрация нежелательной реакции; проверка возможных психотических переживаний. Это схемы обсуждения/ведение процесса, а не готовые персональные назначения.

Файл описывает источники, шаги, условия применимости, наблюдение, сигналы безопасности, пределы и обязательность подтверждения врачом. По умолчанию схемы находятся в каталоге как библиотека; индивидуальный экземпляр назначается через `care_plans` и остаётся черновиком, пока врач не подтвердит его. Никакая схема не назначает препарат автоматически.

`data/guidelines/source_registry.json` — версионированный реестр источников. В него включены WHO ICD-11 CDDR 2024 (это диагностический reference с ограничениями лицензии, не автодиагностика), WHO mhGAP evidence profiles 2023 (профили доказательств, а не индивидуальные схемы), NICE NG222 2022, CANMAT 2023 Update, VA/DoD MDD CPG 2022, копии немецких S3/NVL руководств, российские документы и пользовательский описание клинического сценария. Разные типы источников явно размечены; рекомендации не переносятся механически между системами здравоохранения. Перед клинической эксплуатацией следует отдельно проверить актуальность, локальную применимость и право использования.

`data/medications.json` содержит 17 лекарственных профилей с фармакокинетикой, справочным режимом применения, противопоказаниями, предосторожностями, взаимодействиями, нежелательными реакциями и мониторингом по монографиям «Видаль» и справочным данным стандарта медицинской помощи. Для записей без подтверждённой конкретной регистрации статус требует проверки; адресная ссылка ГРЛС ведёт к поиску по МНН и не подтверждает единственную форму/производителя. Копии российских стандартов 1688/1697 содержат незаполненные реквизиты приказа, поэтому их нельзя принимать за подтверждение действующей редакции. Врач отдельно проверяет актуальную инструкцию/регистрацию по официальному реестру.

## 13. Сигналы безопасности, оповещения и нежелательные явления

`data/red_flags.json` и таблица `red_flag_rules` определяют, что отслеживается, уровень («информационный», «проверить», «срочный», «критический»), источник и адресата (врач, пациент или оба). Врач может включать/выключать предусмотренные правила, менять название, порог и получателей. Получатель «команда ухода» не предлагается, пока в MVP нет состава команды и отдельной модели их прав. Для нового типа сигнала безопасности необходимы схема события, серверная проверка, тесты и описание последствий ложного/пропущенного срабатывания.

Поддерживаются сигналы из текста сообщения, отдельных ответов опросников, структурированного осмотра, дневника и нежелательного явления. Срабатывание по тексту может давать ложные совпадения — исходная формулировка и источник сохраняются для ручного уточнения. Условие на тест сохраняет и отметку риска непосредственно в `questionnaire_results.score_json`, и отдельный alert/notification. Это предотвращает ситуацию, когда флаг есть только в общем списке сигналов, но отсутствует на самом результате теста.

Реестр нежелательных явлений структурирует дату/время, препарат/план, перечень симптомов, выраженность, серьёзность, связь по мнению сообщившего, действие, исход и примечание. Реакции видны в профиле и истории; настроенное правило может уведомить врача, пациента или обоих. Это не автоматическая оценка причинности и не рекомендация самостоятельно отменить/повторить препарат. При экстренных симптомах приложение сообщает не ждать ответа в чате и использовать локальный экстренный протокол.

Уведомления хранятся в приложении с подтверждением прочтения. Web Push может отправляться только при корректно настроенных VAPID-ключах/HTTPS и разрешении пользователя; Android FCM требует Firebase-конфигурации и серверных credentials. Нельзя обещать время реакции врача, фоновую круглосуточную доставку или получение уведомления, пока внешняя инфраструктура не развернута и не испытана.

## 14. Межсистемный обмен и DICOM

- **FHIR R4:** формируется Bundle из существующих Patient, QuestionnaireResponse/Observation, CarePlan/Medication*, AdverseEvent, DiagnosticReport и ImagingStudy данных в объёме, доступном для экспорта. Импорт поддерживает ограниченное подмножество ресурсов и привязывает внешний ID к локальной записи через `external_imports`; повтор того же импорта пропускается. Неизвестные и недопустимые ресурсы не становятся назначениями.
- **CSV/JSON:** импорт нормализованных строк требует явного source system и external ID. Совпадающая запись пропускается вместо молчаливого перезаписывания. Реальные базы потребуют утверждённой схемы соответствия колонок, dry run, журнала ошибок, сверки количества и процедуры отката.
- **DICOM SR:** приложение создаёт минимальный Part-10 Basic Text SR на основе подписанной клинической карты, с ссылкой на source assessment и доступной метаинформацией исследования. Локальные concept codes помечены как локальные, это не официальный код диагноза. DICOM-файл — структурированный отчёт, а не медицинское изображение и не гарантия импорта в любую PACS/модальность.
- **DICOMweb/PACS:** можно сохранить/импортировать метаданные исследования (Study/Series/Instance UID, modality, время, endpoint) и связать их с отчётом. В этой сборке нет полноценного DICOMweb QIDO-RS/WADO-RS/STOW-RS сервера и нет хранения пиксельных данных; изображения остаются в PACS/DICOMweb. Реальный маршрут приёма изображений и профиль SR нужно согласовать с целевой системой и проверить на её тестовом стенде.

FHIR/DICOM export не должен быть вторым местом для ручного ввода. Исходная клиническая запись неизменна после подписания в пользовательском потоке; исправление выполняется отдельной версией/добавлением с аудитом.

## 15. Android, WebView, push и доступность

`android-webview/` содержит исходный проект Android WebView и FCM scaffold, но не готовый/подписанный APK. Для сборки нужны JDK/Android SDK, Gradle wrapper/зависимости и настроенный URL развёрнутого HTTPS backend; для push — Firebase app, `google-services.json`, серверные Firebase credentials и реальные устройства для проверки. Демонстрационный cleartext HTTP ограничен локальным эмулятором; его нельзя использовать для передачи настоящих медицинских данных.

PWA включает manifest/service worker и интерфейс регистрации web push при поддерживаемом браузере. Доступность учитывает крупный текст, `prefers-reduced-motion`, `prefers-contrast` и `forced-colors`, адаптивную компоновку ПК/телефона и доступные текстовые подписи. Это не замена тестированию экранными дикторами, клавиатурой, масштабированием 200–400% и Android Accessibility Scanner.

## 16. Что ещё не считается производственным

1. DICOM Basic Text SR прошёл smoke/Part-10 проверку, но не был подтверждён конкретным PACS/viewer/вендорским профилем.
2. FHIR export/import — реализованное ограниченное подмножество, не сертификат соответствия полному FHIR/профилю организации.
3. Push-заготовки не являются подтверждённой доставкой экстренных уведомлений; нужны retries/ACK/escalation, мониторинг доставки, дежурный процесс и отказоустойчивость.
4. Android shell — исходный код, не скомпилированный APK в этой среде.
5. Все treatment-scheme файлы и red-flag rules требуют клинической валидации, текущести источников и локального утверждения до реального применения.


## 13. Навигация, кликабельная история и календарь

- «История и динамика» размещена сразу после «Пациенты». В шапке врача есть стрелки для переключения между пациентами, список выбора пациента и выбор даты в истории. Справочник имеет поиск, ограниченную страницу результатов, просмотр архива и восстановление; архивирование не удаляет клинические записи.
- Точки графиков выделены визуально, имеют роль кнопки, фокус клавиатуры и подсказку. Клик открывает исходную дневниковую запись/результат и вычисленную интерпретацию шкалы; для старых записей BAI интерпретация может быть восстановлена из действующего ключа инструмента без изменения сохранённой суммы.
- Обзор показывает сигналы текущего пациента, а отдельный раздел сигналов — весь список врача. Детали сигнала содержат источник, время, уровень, обстоятельства и ссылки для перехода к карточке.
- Повторяющиеся ежедневные дозы группируются в один календарный блок на план. Начало, пауза, возобновление и остановка схемы фиксируются отдельными событиями; повторная передача одинакового статуса не создаёт дубликат события. Пациентский экран не показывает внутренние ID и системный тип события.
- DICOM SR выбирает конкретный идентификатор клинического осмотра. Сервер формирует Part-10, а браузер проверяет длину и сигнатуру `DICM`; при отсутствии осмотра файл не скачивается. Совместимость с конкретной PACS/вьюером должна подтверждаться отдельно.
