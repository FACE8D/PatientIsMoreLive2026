# Clinic Companion — локальный MVP для ведения пациента

**Статус:** запускаемый демонстрационный прототип, не медицинское изделие и не система для реального клинического применения. Все встроенные пациентские данные синтетические.

## Что реализовано

- Отдельные роли **«Врач»** и **«Пациент»**, вход по паролю, сессия с ограниченным сроком, CSRF-защита изменяющих запросов и серверная проверка принадлежности карточки врачу.
- Карточка пациента: создать кабинет/связь с врачом, открыть, архивировать без удаления истории; записи приёмов и история действий.
- Дневники настроения/сна/аппетита, питания, поддерживающий чек-лист базовых действий, необязательный мониторинг менструального цикла.
- Библиотека из 14 отдельных JSON-определений шкал и опросников. Баллы пересчитываются на сервере; результат сохраняется с датой и включается в динамику/сводку. Настраиваемые red-flag правила из ответов опросников сохраняют флаг в самом результате и создают отдельный сигнал/уведомление.
- Динамика дневника и результатов; отдельное отображение предупреждений, критических/срочных сигналов и статусов обработки.
- Календарь приёмов и напоминаний по времени, указанному в подтверждённом врачом плане. Пациент может добавить личное событие; врач видит его рядом с клиническими событиями и схемой. Повторяющиеся напоминания по плану отображаются на ближайшие 14 дней. Внешняя синхронизация Google/Apple/Outlook не реализована. Запланированные события можно удалить с подтверждением; фактические, пропущенные и перенесённые события остаются в истории и не удаляются как обычные слоты.
- Библиотека из 11 подключаемых JSON-схем с развёрнутым чтением источников прямо в приложении: содержание метода, шаги, мониторинг, сигналы безопасности, ограничения и разделы/страницы исходных документов. Врач может настраивать конкретный экземпляр схемы для пациента; эти настройки не меняют общую библиотеку. Редактирование активного плана требует повторного обзора и подтверждения врачом.
- Рекомендации врача с черновиком и отдельной публикацией пациенту.
- Чат врача и пациента.
- Единая клиническая карта осмотра: одна структурированная запись питает историю, динамику, FHIR-экспорт и DICOM SR — без повторного набора содержания отчёта. Черновик доступен только врачу; для пациента запись раскрывается после подписи/подтверждения.
- Демонстрационные клинические сценарии: оценка безопасности, выбор маршрута помощи и необходимость профильной консультации.
- Red-flag движок для текста сообщений, ответов опросников, клинической карты, дневника и лекарственных нежелательных реакций. Приоритет/адресат редактируются врачом; получатели в этой версии — врач, пациент или оба (модель команды ухода не реализована).
- Структурированный журнал нежелательных явлений: дата/время, препарат/план, симптомы, выраженность/серьёзность, действие и исход. Запись видна в истории и может уведомлять врача и/или пациента.
- Межсистемный обмен: экспорт ограниченного Bundle FHIR R4, импорт поддерживаемого подмножества ресурсов, идемпотентный CSV/JSON импорт и привязка DICOM Study/Series/Instance metadata. Генерируется DICOM Basic Text SR Part-10 из подписанной клинической карты.
- PWA/service worker, опциональная web push-регистрация и исходный Android WebView + FCM scaffold; пуш требует конфигурации. Журнал аудита, резервное копирование через SQLite Online Backup API и изолированные тесты. Экспорт DICOM SR привязан к конкретной последней сохранённой оценке и проверяет сигнатуру Part-10 перед скачиванием.

## Запуск

Требуется Python 3.10+; сторонние Python-пакеты не нужны.

### Linux / macOS

```bash
cd clinic_companion
./run.sh
```

### Windows

Дважды запустите `run.bat` или выполните его в командной строке.

Затем откройте <http://127.0.0.1:8765/>. По умолчанию сервер привязан только к loopback-интерфейсу, не к публичной сети.

### Демо-учётные записи

- Врач: `doctor@demo.local` / `DemoDoctor2026!`
- Пациент: `patient@demo.local` / `DemoPatient2026!`

Это общие демонстрационные пароли. Не используйте их для настоящих учётных записей. Демо-режим по умолчанию добавляет синтетического пациента и записи; выключить создание демо-данных можно переменной `CLINIC_DEMO_MODE=0` при первичном запуске.

### Переменные окружения

- `CLINIC_HOST` — по умолчанию `127.0.0.1`; для обычного безопасного локального запуска не менять.
- `CLINIC_PORT` — по умолчанию `8765`.
- `CLINIC_DB_PATH` — путь к SQLite-файлу; по умолчанию `data/clinic.db`.
- `CLINIC_DEMO_MODE` — `1` (по умолчанию) создаёт демо-сценарий, `0` отключает.

Для изолированного теста рекомендуется задавать отдельный `CLINIC_DB_PATH`.

## Версия для слабовидящих

В верхней панели есть кнопка «Для слабовидящих». Она включает увеличенный текст, более высокую контрастность и заметную рамку клавиатурного фокуса; настройки сохраняются в этом браузере. В разделе настроек можно независимо выбрать крупный текст и высокую контрастность. Интерфейс также учитывает системные настройки уменьшения анимации, повышенной контрастности и принудительной цветовой схемы. Рекомендуется дополнительно проверить приложение с экранным диктором и увеличением 200–400% на целевых устройствах.

## Клинические схемы и реестр источников

11 подключаемых схем лежат в `data/treatment_schemes/*.json`, список лекарственных справочных карточек — в `data/medications.json`, правила сигналов безопасности — в `data/red_flags.json`, версии/типы руководств и источников — в `data/guidelines/source_registry.json`, интеграционные возможности и ограничения — в `data/integrations.json`. Манифест `clinical_library_manifest.json` фиксирует версии и SHA-256. Среди схем: оценка тревоги; сопровождаемая самопомощь; структурированная КПТ; поведенческая активация; посильная физическая активность; релаксация; проверка начала/мониторинга антидепрессанта; профилактика рецидива; постепенное снижение/отмена; проверка возможной психотической симптоматики; оценка нежелательных реакций.

Реестр различает клинические руководства, evidence profiles и справочные/стандартные документы. Например, NICE NG222 опубликован в 2022 году, CANMAT — обновление 2023 года (статья 2024), WHO mhGAP evidence profiles являются профилями доказательств, а немецкая S3-копия указывает плановый пересмотр в 04/2026. Актуальность и локальная применимость обязательно подтверждаются перед клиническим применением. Российские копии стандартов в присланном наборе имеют незаполненные реквизиты приказа; они не рассматриваются как подтверждение текущего правового статуса. Схемы не подбирают дозы и не назначают лечение автоматически.

## Подробные схемы, лекарственные карточки и ГРЛС

В разделе «Библиотека схем и препараты» карточка метода открывает встроенное окно с развёрнутым содержанием по приложенным документам, источниками и ограничениями — не требуется постоянно переключаться между файлами. Из выбранной схемы врач может создать план конкретного пациента, отредактировать поля настройки этого экземпляра и сохранить его как черновик. Для активного плана изменение параметров требует нового клинического обзора и подтверждения.

Карточка препарата открывается отдельной кнопкой и показывает собранное описание, фармакологическую группу и код анатомо-терапевтической классификации, упоминания в источниках, доступные сведения о средних суточных/курсовых дозах и ограничения этих данных. Для «Авиандра®» дополнительно отображается структурированная выдержка опубликованной инструкции с ссылкой на её источник. Для 16 оставшихся МНН из таблицы стандарта дополнительно представлены фармакокинетические и справочные сведения из монографий «Видаль»; моклобемид и милнаципран исключены из нового каталога по вашему указанию как неподходящие для доступных назначений. В карточках отдельно обозначено, какие данные относятся к действующему веществу, а какие — к конкретному зарегистрированному продукту. Средняя суточная/курсовая доза из стандарта не является персональным назначением и не заменяет инструкцию конкретной лекарственной формы.

Кнопка ГРЛС формирует адресный поиск по МНН, а не ведёт на общую главную страницу реестра. Поскольку стандарт 1697 не указывает торговое наименование, держателя регистрации, форму выпуска и конкретный регистрационный номер для большинства МНН, приложение не выбирает случайную карточку одного производителя: после открытия результатов врач должен выбрать точную зарегистрированную форму и сверить действующую инструкцию. Ссылка на опубликованную инструкцию «Авиандр®» ведёт на страницу конкретного листка-вкладыша, но она также не заменяет проверку текущего статуса/редакции в ГРЛС.

**Особое замечание к источнику:** в таблице стандарта первичной медико-санитарной помощи при депрессиях (ремиссии), печатная страница 6, для флуоксетина единица указана как «мл». Она сохранена буквально и помечена в карточке как требующая проверки; приложение не исправляет сомнительную единицу догадкой, а запрещает использовать эти значения как назначение до сверки с оригиналом и актуальной инструкцией. Копия стандарта имеет незаполненный номер приказа, поэтому правовая актуальность не считается подтверждённой.

## Отдельный набор опросников

Файлы находятся в `data/questionnaires/*.json`; сервер читает их при запросе каталога/конкретной шкалы, поэтому тексты, варианты ответов и конфигурация расчёта отделены от серверного кода и интерфейса.

Каждый файл включает `id`, `title`, `category`, `respondent`, `instruction`, `source`, `version`, `questions[]`, `scoring` и `license_review_required`; некоторые определения включают `implementation_notes`. Структуру и требования описывает `data/questionnaires/README.md`. Не заменяйте версию опросника под тем же ID без изменения версии и повторной проверки результатов.

Чтобы добавить новый инструмент: создайте отдельный JSON по существующей схеме; укажите источник/версию и право цифрового воспроизведения; определите все scoring rules на сервере в `server.py`; добавьте автоматические тесты на граничные баллы и рисковые пункты. Не допускайте, чтобы произвольный клиент передавал готовый результат — сервер обязан считать его из ответов.

`build_questionnaires.py` документирует/воспроизводит исходные определения, созданные из приложенных материалов; запуск перезаписывает JSON-файлы пакета, поэтому перед ручной редактурой сначала внесите изменение в генератор или сохраните резервную копию.

Тесты используют только временные базы и синтетические данные. Кроме CRUD/ролей/опросников проверяются скрытие черновиков, сигнал безопасности в сообщении и непосредственно в результате теста, подписанная клиническая карта, запрет доступа к неподписанному осмотру, FHIR/DICOM-вывод, идемпотентный импорт, перечень побочных реакций, открытие карточки препарата, адресный поиск ГРЛС, чтение подробной схемы в приложении, редактирование параметров конкретного плана и переносимость текста нежелательной реакции на мобильном viewport.

Создать консистентную резервную копию текущей БД: `python backup_db.py` (резервная копия не шифруется автоматически — храните её в защищённом месте). Указать явно: `python backup_db.py --db data/clinic.db --out backups/clinic-backup.sqlite3`.

## Ограничения и безопасность

1. **Не использовать для диагностики или лечения реальных пациентов.** Не загружайте идентифицирующие или медицинские сведения в демо-сборку. Тесты, правила алертинга и программный код не проходили клиническую валидацию.
2. Приложение сохраняет внутренние уведомления. Web Push/Android FCM отправляются только при фактической настройке VAPID/Firebase и проверке доставки. В этой сборке нет гарантированной круглосуточной эскалации, SLA, дежурного персонала или гарантии уведомления при закрытом браузере. Пациенту явно сообщается, что при угрозе жизни нельзя ждать ответа приложения.
3. Нет встроенной локальной обученной LLM. В текущем релизе структура построена вокруг правил безопасности и клинической карты, без автономного вывода диагноза. Любые AI-функции следующего этапа должны работать через структурированный контракт и врачебное подтверждение.
4. Карточка «Авиандр®» содержит ссылку на опубликованную инструкцию, но текущая запись ГРЛС и актуальность инструкции не подтверждаются автоматически. Для каждого МНН ссылка открывает адресный поиск, а не гарантированно единственную запись: нужно сверить производителя, форму, дозировку и регистрационный номер. Используйте официальный <https://grls.rosminzdrav.ru/> и не рассматривайте эти карточки как персональное назначение. Автоматического подбора препарата/дозы нет. Таблица стандарта первичной медико-санитарной помощи при депрессиях (ремиссии) указывает для флуоксетина «мл»; значение сохранено как в источнике и явно требует сверки.
5. Для части шкал необходима проверка разрешения на копирование/цифровое распространение и условий использования. Это отражено в JSON и интерфейсе. HCL-32 и HCL-33 сохранены раздельно. C-SSRS доступна врачу, требует обученного специалиста; числовой суммарный балл не вычисляется.
6. Прежде чем любой клинический запуск, нужны как минимум: проверка действующих источников/лицензий специалистами; проверка правил и текстов клиницистами; тестирование с контролируемыми сценариями; HTTPS и безопасная аутентификация/восстановление доступа; шифрование диска и резервных копий; политика согласия, доступа, хранения и удаления; threat-model и независимый аудит; реальная доставка/эскалация оповещений; резервное копирование и проверенное восстановление; оценка применимого законодательства и требований к медицинскому ПО/персональным данным.

## Документация

- `ARCHITECTURE.md` — компоненты, потоки данных, границы безопасности и план локальной модели.
- `data/questionnaires/README.md` — формат, список файлов и оговорки психометрических шкал.
- `data/medications.json` — отдельная библиотека лекарственных карточек.
- `data/demo_scenarios.json` — синтетические клинические демонстрации.
- `SIX_PATIENT_DEMO.md` — продольные сценарии шести портретов и инструкция по демонстрации кликабельной истории.
- `data/treatment_schemes/` и `data/guidelines/source_registry.json` — загружаемая библиотека методов и реестр источников.
- `data/red_flags.json` — исходный набор правил безопасности.
- `interoperability.py` — сериализация FHIR R4 и DICOM SR.
- `android-webview/README.md` — Android WebView/FCM scaffold и инструкции настройки.

### DICOM, FHIR и Android

- FHIR R4: ограниченное подмножество экспорта/импорта. Требуется проверка соответствия профилю принимающей организации и терминологиям.
- DICOM: генерируется Basic Text SR Part-10 на основе подписанной записи; DICOM images/pixel data приложение не хранит и не предоставляет DICOMweb QIDO/WADO/STOW сервер. Изображения остаются на PACS/DICOMweb; поддерживается привязка метаданных исследования/UID. Полученный SR надо проверить на тестовой целевой PACS/модальности.
- Android: в архиве есть исходный WebView/FCM scaffold, но не подписанный APK. Для сборки нужны Android SDK/JDK/Gradle, адрес HTTPS-развёртывания и Firebase-проект.


## Доступность и лекарственная библиотека

- Кнопка «Для слабовидящих» в верхней панели включает увеличенный текст, повышенную контрастность и хорошо заметный фокус клавиатуры; настройки запоминаются в браузере. Можно отдельно выбрать крупный текст и высокую контрастность. Системные режимы `prefers-contrast`, `forced-colors` и `prefers-reduced-motion` также учитываются.
- В разделе «Схемы и препараты» у врача есть кнопка «Сравнить препараты». Сравниваются фармакологическое действие, показания из справочника, фармакокинетика, справочные режимы, противопоказания, меры предосторожности, взаимодействия, нежелательные реакции, мониторинг и статус регистрации.
- В карточках источники называются по заголовкам монографий/рекомендаций. Имена входных файлов не выводятся в интерфейсе. Сводные списки противопоказаний и взаимодействий помечены как не исчерпывающие и не заменяют полную актуальную инструкцию конкретного продукта.
- Для 19 препаратов собраны профили фармакокинетики и клинических ограничений по монографиям справочника «Видаль»; для «Авиандра®» также добавлена отдельная страница конкретного препарата. Сводные перечни противопоказаний, взаимодействий и нежелательных реакций не следует считать полными; отсутствие пункта не подтверждает отсутствие риска. ### Рекомендуемый сценарий демонстрации

1. Войдите под врачом и откройте «Пациенты». Выберите карточку, затем «История и динамика». Вверху видны длительность наблюдения, полнота дневника, доля зарегистрированных приёмов, число дней без отметки и число отклонений.
2. На графике настроения нажмите точку — откроются дневниковые записи за этот день или недельный интервал. В графике шкал нажмите точку, чтобы увидеть исходные ответы и значение. Исходные баллы из портрета отмечены отдельно от смоделированных последующих измерений.
3. В фильтре «Отклонения» выберите пропуск визита, пропуск лекарства, низкое настроение, рост шкалы или red flag — каждая строка открывается в отдельном подробном окне с первичной записью. Незаполненный журнал лекарства показывается как «нет отметки», а не автоматически как доказанный пропуск.
4. В календаре нажмите запланированный приём, затем «Перенести приём». Система сохраняет исходное событие как перенесённое, создаёт новый слот и записывает причину. Из того же окна врач может отметить состоявшийся или не состоявшийся приём; неявка создаёт отдельный сигнал.
5. Переключитесь на соответствующий пациентский аккаунт, заполните настроение, питание, базовые действия, отметку приёма или сообщение врачу. После обновления карточки врача новые записи и обратная связь появляются в той же истории.

**Важно:** все шесть профилей и всё наблюдение после исходной оценки синтетические. Суммы шкал в исходном портрете сохранены; последующие измерения намеренно моделируют разные сценарии улучшения, ухудшения и неполной приверженности исключительно для проверки работы приложения.

Для старых BAI-результатов применяется интерпретация по ключу, когда сохранённая запись не содержит поля интерпретации; это не меняет исходный балл.
- В «Обзоре» показываются сигналы выбранного пациента; отдельный раздел сигналов предназначен для всех пациентов. Кнопка сигнала открывает подробности, связанную статистику и переход в карточку.

- Источник NICE NG222 предлагает прямые ссылки на обзор и главу рекомендаций. В карточках препаратов доступны приложенные листки-вкладыши PDF по локальным ссылкам; имена исходных файлов не показываются в карточках.
- Календарь обобщает ежедневный приём в одном повторяющемся событии на план, чтобы не затенять приёмы. Пауза, возобновление и остановка плана отражаются отдельным событием с датой, временем и причиной. Пациент не видит внутренних идентификаторов и служебного типа события.

## Исправления по обратной связи: переключение пациентов, календарь и сообщения

- Переключатель пациентов в верхней панели не должен терять список после открытия другой карточки. Выбор в списке и стрелки должны загружать другой профиль и обновлять графики, историю, календарь, назначения и чат. Справочник пациента остаётся на своей странице, а выбранная карточка добавляется к вариантам выбора отдельно.
- Запланированное событие календаря можно удалить через окно подробностей. Удаление выполняется как мягкое: статус меняется на `deleted`, действие попадает в аудит; при удалении врачом пациенту отправляется внутреннее уведомление. Завершённые, пропущенные и перенесённые события, а также системные изменения плана лечения нельзя удалить как обычный слот.
- Отправитель может исправить или удалить собственное сообщение. При исправлении сервер сохраняет предыдущий и новый текст, причину, дату и автора. При удалении исходный текст сохраняется в защищённой базе/журнале, а обычная переписка показывает «Сообщение удалено отправителем». Врач может открыть историю изменений. Нельзя изменять или удалять сообщение другого участника.
- Регрессионная проверка: `python tests/browser_ui_test.py` проверяет переключение пациента туда-обратно, удаление события и редактирование/удаление сообщения; `python tests/smoke_test.py` проверяет серверные права, аудит и мягкое удаление на временной базе.

## Регрессионные и эксплуатационные проверки

В дополнение к функциональным тестам доступны два воспроизводимых вспомогательных прогона:

```bash
python tests/performance_smoke.py
python tests/backup_recovery_test.py
```

`performance_smoke.py` запускает сервер с отдельной временной SQLite-базой и выдаёт p50/p95/p99 для `/api/health`, `/api/bootstrap` и карточки пациента при небольшой параллельной нагрузке. Это локальный smoke benchmark, а не сертификат производительности или предел одновременных пользователей. Можно задать `CLINIC_BENCH_REQUESTS` и `CLINIC_BENCH_WORKERS`.

`backup_recovery_test.py` проверяет резервное копирование через SQLite Online Backup API, `PRAGMA integrity_check` и открытие восстановленной копии. Это подтверждает базовый механизм восстановления, но не задаёт гарантий RPO/RTO для production.

Браузерный тест ограничен таймаутами запуска/селекторов, чтобы ошибка интерфейса завершала прогон, а не зависала неопределённо. Контейнер уведомлений не перехватывает клики по интерфейсу под ним.
